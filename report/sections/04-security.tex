\section{Security Design}
\label{sec:security}

\subsection{Authentication and Session Lifecycle}
Passwords are hashed with Argon2id. On successful sign-in, Identity issues a
short-lived (10-minute) RS256-signed JWT access token carrying the subject,
tenant, role and permission set, plus an opaque refresh token delivered as an
\texttt{HttpOnly}, \texttt{Secure}, \texttt{SameSite=Strict} cookie. Refresh
tokens are stored server-side only as a salted hash, rotate on every use, and
are tracked in families: replaying an already-used refresh token revokes the
entire family and forces re-authentication
(\cref{fig:d3c-sequence-auth}). Sessions carry an absolute lifetime (8~hours)
and an idle timeout (30~minutes), independent of the access-token expiry, so a
revoked or expired session is rejected by Identity's validation endpoint even
if an access token has not yet expired. Five consecutive failed password
attempts lock the account for 15~minutes, tracked atomically per user.

\subsection{Authorization}
Every permission check happens twice: the frontend hides controls the active
role cannot use (usability), and every API handler independently re-checks
the caller's permission set and resource ownership from the validated JWT
claims -- never from a client-supplied header, query parameter or body field.

\subsection{Multi-Tenant Isolation}
Every tenant-owned table carries a \texttt{tenant\_id} column. Isolation is
enforced in two independent layers: (1)~the application sets the active
tenant as transaction-local PostgreSQL state
(\texttt{set\_config('app.tenant\_id', \dots, true)}) and every query carries
an explicit tenant predicate; (2)~PostgreSQL row-level security policies with
\texttt{FORCE ROW LEVEL SECURITY} additionally block any row whose
\texttt{tenant\_id} does not match the session variable, even if application
code were to omit a predicate by mistake. The database runtime role used by
each service has no table ownership and no \texttt{BYPASSRLS} attribute.
Automated tests assert that an authenticated user of tenant~A receives a
non-disclosing 404 (not the record) when requesting any object ID that
belongs to tenant~B, across every list, detail, export and dashboard
aggregate endpoint exercised in the test suite.

Additionally, all cookie-authenticated state-changing endpoints
(\texttt{/auth/refresh}, \texttt{/auth/logout}) require both an
allow-listed \texttt{Origin} header and a matching CSRF token supplied
out-of-band from the refresh cookie, mitigating CSRF; all API responses set
\texttt{X-Content-Type-Options: nosniff} and a restrictive
\texttt{Content-Security-Policy}, mitigating stored/reflected XSS in
combination with React's default output escaping.

\subsection{Transport and Webhook Security}
The mobile-money simulator's callback is authenticated by an HMAC-SHA256
signature over the request body and a timestamp, rejecting requests whose
signature does not match or whose timestamp is outside a five-minute window
-- never by a normal user session, since the caller is an external system.
The QR attendance challenge is similarly a signed, tenant-bound, 60-second
token, not a bare reusable employee identifier (\cref{sec:hr-module}).
